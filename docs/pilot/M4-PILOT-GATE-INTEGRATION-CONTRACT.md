## Evidence source and verification boundaries

- SHA-256 verifies exact input bytes **against the saved one-time collection pin**, not truth of narrative, human reviewer identity, signature authenticity, target ownership or provenance outside that file. Replacing the manifest itself breaks independent review and requires a new chain-of-custody evaluation.
- Strict UTF-8/JSON/bounded size and exact run ID/delivery/baseline checks. Duplicate input IDs, malformed signatures, false `main_apply` stage, wrong scope/role, older-than-90-day collection, future collection time, path traversal and symlink escape fail closed.
- A genuine `SHARE-SUMMARY.json` must have `prior_summary` fields, recorded `APPLIED_VERIFIED`, no file hash conflict and requisite QA stages PASS. An absent file does not become PASS from terminal prose; it is `MISSING_EVIDENCE`.
- Review of edition, media, legal and policy is version-specific. If reviewed bindings do not match current hashes, report `STALE_REVIEW_REQUIRED`. Approvals supplied as JSON text cannot authenticate a reviewer and must not change a final gate status.
- Technical FIG statuses are sourced from `App\Support\FigP4OperationalEvidence::reconcile()` and always distinguish synthetic/partial from external field acceptance. Exactly `AC-FIG-01..12` must appear; no AC-13.
